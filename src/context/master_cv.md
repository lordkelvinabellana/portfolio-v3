# Major Automation Project — OnlineJobsPH Auto-Matching System

One of the automation systems I am most proud of is my OnlineJobsPH automation because it directly solved a personal operational problem using real production logic.

The problem:

manually refreshing job boards repeatedly wastes time and creates poor decision-making because quantity overwhelms quality.

The goal:

create a system where only high-quality opportunities reach me.

## Full Workflow

### Step 1 — Job Scraping

A cron job runs every 5 minutes and scrapes new OnlineJobsPH job listings automatically.

### Step 2 — Normalization + Deduplication

The system normalizes new listings and compares them against existing stored jobs inside Google Sheets.

Duplicate jobs are automatically removed to prevent repeated processing and spam.

### Step 3 — Keyword Filtering

Before using the LLM layer, listings are filtered using strong keywords and rejection keywords.

This reduces unnecessary token usage and protects the AI layer from low-quality jobs.

### Step 4 — AI Matching Layer

The filtered jobs are passed into an LLM workflow where AI compares each job against:

- my skills
- role preferences
- salary expectations
- technical fit
- workload expectations

The AI returns:

- match score
- pros
- cons
- summary
- salary-to-workload reasoning
- shouldApply decision
- job link

### Step 5 — Quality Filtering

Only jobs where:

- shouldApply = true
- match score ≥ 75

continue forward.

This removes spam notifications and prioritizes quality over quantity.

### Step 6 — Smart Notification

The system generates an HTML email containing:

- job details
- AI analysis
- recommendation summary
- direct job application button

The final button links directly to the original job post for fast action.

This creates a true “auto-matching” system rather than simple scraping.

## Infrastructure

Built using:

- self-hosted n8n
- Oracle Cloud free tier VM
- Google Sheets
- OpenAI workflows
- scheduled cron jobs

This project is a strong example of how I think:

not just automation for automation’s sake,

but practical systems that improve real decisions.

# Major Automation Project — AutoFit Weekly Coaching System

Another major automation project I built was for a coaching business where the main problem was not messaging clients, but the heavy manual work required before those messages could even be written.

The coach had to manually review each client’s weekly progress data, compare changes, understand context, and then write personalized weekly coaching updates one by one.

This became repetitive, time-consuming, and difficult to scale as the number of clients increased.

The goal was not to replace the coach, but to remove the repetitive analysis work while keeping human approval and relationship quality intact.

## System Goal

Transform:

manual review → manual writing → manual sending

into:

AI analysis → draft generation → coach approval → final sending

while preserving human control.

## Workflow Logic

### Weekly Snapshot Collection

The system first creates weekly client snapshots as immutable records.

These snapshots act as the source of truth and preserve weekly progress history without overwriting older states.

This was important because coaching decisions should be based on observation, not overwritten live values.

### AI Analysis Layer

The automation compares:

- previous client progress
- latest check-in data
- behavior trends
- weekly habits
- coaching context

The AI then generates:

- progress summaries
- coaching observations
- motivational messaging
- personalized weekly recommendations

The goal was to sound supportive, useful, and human, not robotic.

### Coach Approval Layer

Before anything is sent to clients, the generated message is sent to the coach for approval.

The coach can:

- approve directly
- request edits
- provide manual notes
- reject the message entirely

If edits are requested, the AI regenerates the message using the feedback instead of rewriting from scratch manually.

### Final Delivery

Only after approval does the system send the final personalized coaching message to the client.

This preserved trust while dramatically reducing the manual preparation workload.

## Key Result

The biggest value was reducing the coach’s mental workload, not just saving time.

Instead of manually reviewing every client from scratch every week, the coach could focus on reviewing strong recommendations and maintaining client relationships.

This created better consistency and scalability without losing personalization.

## Technical Notes

Built using:

- n8n
- weekly snapshot architecture
- approval state management
- AI regeneration loops
- client state tracking
- message approval workflows
- WhatsApp messaging logic

This project became a strong example of combining AI with human oversight instead of replacing judgment entirely.

That philosophy is something I strongly believe in when designing AI workflows.

# Major Automation Project — Zoom Recording to YouTube Pipeline

One of the more technically frustrating automation projects I worked on involved moving a large backlog of Zoom recordings into YouTube automatically.

The goal seemed simple:

download Zoom recordings → upload to YouTube → update tracking status

but the execution exposed infrastructure limitations that made the problem far more difficult than expected.

## Workflow Goal

Automate:

- Zoom recording retrieval
- download handling
- YouTube upload
- Google Sheets tracking
- status visibility across large historical backlogs

This was especially important because the client had years of recordings dating back to 2021 and needed reliable upload tracking.

## Core Challenge

The major blocker was binary file handling.

Large recordings such as one-hour meetings exceeded n8n’s execution limitations and often failed because binary downloads hit timeout limits before completion.

This was not a logic problem.

It was an infrastructure problem.

## What I Explored

I researched and proposed multiple solutions including:

- S3 bucket storage
- alternative object storage solutions
- Oracle-based storage options
- official n8n Cloud
- moving away from binary-heavy local handling

The goal was to shift downloads away from direct binary execution and into more scalable storage architecture.

## Real Lesson

The technical solution existed.

The blocker was budget.

The client refused additional infrastructure cost despite multiple practical solutions being proposed.

Without storage flexibility, the workflow could not be completed reliably.

Eventually the project ended because execution could not move forward without investment.

## What I Learned

This project taught me that technical limitations are often business limitations.

Sometimes the problem is not code.

It is willingness to support the right architecture.

That lesson became very valuable for future automation consulting work.

Because the best solution is only useful if the decision-maker is willing to support it.

# Difficult Client Story — Zoom Automation Project

One of the most difficult freelance experiences I had involved automating Zoom recording uploads to YouTube.

The workflow itself was valid.

The issue was infrastructure.

Large recordings kept failing because binary downloads exceeded execution limits inside n8n.

I researched multiple solutions:

- S3 bucket storage
- alternative object storage
- Oracle-based options
- n8n Cloud
- architecture changes away from direct binary handling

The real solution was clear.

The blocker was budget.

The client refused any infrastructure cost increase even when it was necessary for the workflow to succeed.

At that point, the problem stopped being technical.

It became a business decision problem.

Eventually I ended the project because progress was impossible without basic architectural support.

The lesson was important:

sometimes the limiting factor is not code.

It is decision-making.

That experience made me much better at evaluating project feasibility early.

# Product Thinking Story — RentWise

One of the strongest product lessons came from building RentWise.

- scoring systems

The technical build mattered, but the product thinking mattered more.

software should reduce bad decisions, not just create new screens.

That mindset affects how I approach almost every product now.
